What Are SOLID Principles?

SOLID is a group of five object-oriented design principles. They help developers write code that is easier to understand, maintain, test, and extend.

SOLID does not mean that every class must always follow every principle perfectly. Use these principles as guidelines for making design decisions.
S — Single Responsibility Principle

A class should have one clear responsibility and one main reason to change.

Keep related responsibilities together instead of putting unrelated tasks into one large class.
O — Open/Closed Principle

Software entities should be open for extension but closed for modification.

Add new behavior through extension instead of repeatedly changing stable existing code.
L — Liskov Substitution Principle

Objects of a child class should be usable wherever the parent class is expected without breaking the program's behavior.

I — Interface Segregation Principle

A class should not be forced to implement methods that it does not need.

Prefer small, focused interfaces instead of one large interface containing unrelated methods.
D — Dependency Inversion Principle

High-level modules should depend on abstractions rather than directly depending on low-level implementation details.

Interfaces are commonly used to create flexible dependencies.

Single Responsibility Principle

Problem

Imagine one class responsible for employee information, database operations, and report generation. 

class Employee {

    void saveToDatabase() {
        // Database code
    }

    void generateReport() {
        // Report code
    }

    void calculateSalary() {
        // Salary calculation
    }
}

Better Design

class Employee {
    // Employee information
}

class EmployeeRepository {
    // Database operations
}

class EmployeeReport {
    // Report generation
}

Open/Closed Principle

Instead of changing existing code every time a new type is added, use abstraction and inheritance to extend behavior. 

interface Payment {
    void pay();
}

class UPIPayment
        implements Payment {

    public void pay() {
        System.out.println("Paid using UPI");
    }
}

class CardPayment
        implements Payment {

    public void pay() {
        System.out.println("Paid using Card");
    }
}
A new payment method can be added by creating another implementation instead of rewriting the existing payment classes.

Liskov Substitution Principle

A subclass should behave in a way that remains compatible with the expectations of its parent type. 

class Bird {
    void eat() {
        System.out.println("Bird is eating");
    }
}

class Sparrow
        extends Bird {

    void fly() {
        System.out.println("Sparrow is flying");
    }
}

Sparrow can be used wherever a Bird is expected without breaking the basic behavior defined by Bird.

Interface Segregation Principle

Large Interface Problem

interface Worker {

    void work();

    void eat();

    void sleep();
}

If a class does not need all these operations, it should not be forced to implement them.

Better Design

interface Workable {
    void work();
}

interface Eatable {
    void eat();
}

interface Sleepable {
    void sleep();
}

Dependency Inversion Principle

High-level classes should depend on abstractions rather than concrete implementation classes. 

interface NotificationService {
    void send(String message);
}

class EmailService
        implements NotificationService {

    public void send(String message) {
        System.out.println("Email: " + message);
    }
}

class OrderService {

    private NotificationService notification;

    OrderService(
            NotificationService notification) {

        this.notification = notification;
    }

    void placeOrder() {
        notification.send("Order placed");
    }
}
OrderService depends on the NotificationService interface, not directly on EmailService.

Dependency Injection

The previous example demonstrates a simple form of constructor dependency injection. 

NotificationService service =
        new EmailService();

OrderService order =
        new OrderService(service);

order.placeOrder();
Email: Order placed

SOLID Summary

Letter Principle Main Idea
S Single Responsibility One clear responsibility
O Open/Closed Extend without repeatedly modifying stable code
L Liskov Substitution Subclasses should remain compatible with parent types
I Interface Segregation Prefer small focused interfaces
D Dependency Inversion Depend on abstractions

Good OOP Design

  • Keep classes focused.
  • Use meaningful names.
  • Hide internal implementation details.
  • Prefer composition when appropriate.
  • Use interfaces for flexible dependencies.
  • Avoid unnecessary inheritance.
  • Keep methods small and understandable.

Common Design Problems

  • Very large classes
  • Too many responsibilities
  • Tight coupling
  • Repeated code
  • Deep and unnecessary inheritance
  • Large interfaces
  • Direct dependency on implementations

OOP Design Checklist

  1. Does each class have a clear responsibility?
  2. Can new functionality be added without changing too much existing code?
  3. Are subclasses compatible with their parent types?
  4. Are interfaces small and focused?
  5. Do high-level classes depend on abstractions?
  6. Is the code easy to test?
  7. Is the code easy for another developer to understand?
